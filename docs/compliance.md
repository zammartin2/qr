# ISO/IEC 18004 compliance

**Русская версия:** [ru/compliance.md](ru/compliance.md)

`@fab-orbita/qr` targets full conformity with ISO/IEC 18004 (QR code bar code symbology specification) for the parts it implements — see the "out of scope" row below.

This document covers three things: what is implemented, where the spec is ambiguous and which reading this library pins, and how the implementation is verified against the reference `qrcode` package.

## Interpretation notes

### N4 penalty (dark-module ratio)

The standard describes N4 as the deviation from 50% measured "in steps of 5%". Two readings exist for boundary values (e.g. 51%, 56%): truncation (`floor(|p − 50| / 5)`, used by zxing) and ceiling (`|ceil(p / 5) − 10|`, used by node-qrcode and by this library).

**Decision:** this package pins N4 to the node-qrcode semantics so that automatic mask selection matches the reference implementation byte-for-byte (verified by the test corpus). The difference only shifts the penalty at boundary percentages; in practice it does not change the chosen mask for typical inputs, and both readings produce scannable symbols.

### N3 penalty (finder-like pattern)

Implemented exactly as specified: an 11-module window matching `1011101` preceded **or** followed by four light modules counts 40 points. A pattern with light areas on both sides produces two overlapping 11-module windows, each scored independently — 80 points total. This is the behavior specified by ISO/IEC 18004, not an artifact of the implementation. Rows and columns are both scanned; only full 11-module windows are considered.

### Kanji mode

- Characters are mapped Unicode → Shift JIS via a committed table generated by `scripts/gen-kanji-map.mjs`: every double-byte pair inside `0x8140–0x9FFC` and `0xE040–0xEBBF` is decoded with Node's built-in `TextDecoder('shift_jis')`. On collisions — the same Unicode code point mapping from multiple Shift JIS codes, which happens for vendor-extension duplicates — the lowest SJIS code is kept. This is deterministic.
- Range adjustment follows the standard: first range subtracts `0x8140`, second subtracts `0xC140`, then `value = high × 0xC0 + low` (13 bits).
- The table round-trips through `TextDecoder` for **every** entry in the test suite (6 953 characters: kana, kanji, JIS X 0208 Cyrillic/Greek, symbols).
- The committed table costs ~111 KB raw / ~6 KB gzipped, keeps the package dependency-free, and is deterministic across runtimes.
- Kanji is never auto-detected (see `docs/api.md`).

### Byte mode count indicator

The character count for byte mode is the number of **UTF-8 bytes** (ISO/IEC 18004:2015 §7.4.4), not the number of JavaScript string code units. This library follows the standard.

### Empty input

`generateQR('')` is allowed and produces a version-1 byte-mode symbol with an empty data segment. The reference `qrcode` package rejects empty input, so empty input is excluded from the 1280-matrix comparison and the fuzz corpus and is tested separately against ISO capacity anchors.

## Verification strategy

The reference implementation is `qrcode@1.5.4`, pinned in `devDependencies`. Bumping it requires re-running the parity suite and reviewing any diff.

- **1280 matrix comparisons**: every version (1–40) × EC level (4) × mask (8) against `qrcode@1.5.4` with forced version, forced mask and forced single-segment inputs — byte mode, plus numeric/alphanumeric/UTF-8 corpus subsets. Zero differing cells. Automatic version and mask selection are covered separately (next bullet).
- **Automatic version + mask parity** on a fixed corpus and a 200-string seeded fuzz run.
- EC table cross-checked against the reference for all 160 combinations, plus structural invariants and ISO byte-capacity anchors.
- Format/version BCH words compared against the reference for all 32 and all 34 versions respectively; ISO anchors pinned (`v7 = 0x07C94`, `L/0 = 111011111000100`, `M/0 = 101010000010010`).
- Reed–Solomon encoder byte-compared against the reference on random inputs; syndrome-zero property asserted.
- PNG output decoded back (`inflate`, pixel sampling) for **both** the Node and the browser entries; the IEND CRC is pinned to the well-known `0xAE426082`.

The parity and fuzz tests live alongside the source; see `CONTRIBUTING.md` for how to run them and what to add when touching the pipeline.
