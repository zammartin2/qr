# Производительность

**English:** [../performance.md](../performance.md)

## Методика

Запуск набора бенчмарков:

```bash
npm run bench  # сначала собирает dist/, затем запускает scripts/bench.mjs
```

Описываемая ниже процедура бенчмарка использует:

- 10 000 итераций на вход после прогрева в 500 итераций.
- Идентичные входы для `@fab-orbita/qr` и `qrcode@1.5.4` (точный корпус — `scripts/bench.mjs`).
- Уровень коррекции ошибок `M`, автовыбор версии и маски у обеих библиотек.
- Результаты дописываются в `benchmarks/history.json`.

Приведённые цифры — из **двух записанных прогонов бенчмарка**, а не из статистически контролируемого ряда. Их не следует трактовать как доказательство устойчивого преимущества в скорости или регрессии.

## Записанные результаты

Окружение для этих прогонов: Node.js v22.23.3, Linux x64, 2026-10-08. Модель CPU, версия V8, идентификатор коммита и детальная статистика вариативности в предоставленных результатах зафиксированы не были.

| 40 цифр | 2 281,4 мс | 2 187,5 мс | `fab-qr` на 4,3% медленнее |

### Интерпретация

В этих двух прогонах общая пропускная способность была в целом сопоставима с `qrcode@1.5.4`:

- **URL:** паритет; направление отрыва менялось между прогонами.
- **Английский текст:** `fab-qr` был быстрее в обоих прогонах, но наблюдаемое преимущество заметно варьировалось (примерно 2,9–10,6% относительно времени `qrcode`).
- **Числовой режим:** `fab-qr` был медленнее в обоих прогонах (примерно 4,3–6,4% относительно времени `qrcode`). Это **воспроизводимое наблюдение в этой малой выборке**, а ещё не доказательство того, что причиной именно числовой энкодер или что разница статистически значима.

Отдельные измеренные тайминги менялись между двумя прогонами примерно на 8% (URL-нагрузка для `fab-qr`). Это **наблюдаемая вариативность между прогонами**, а не установленная граница шума ±8%. Для оценки вариативности и надёжных выводов требуются более независимые повторы на контролируемом железе.

**Вывод:** имеющихся данных достаточно, чтобы описать производительность как в целом *сопоставимую* с эталоном, с возможным недостатком на числовой нагрузке, который стоит исследовать. Не следует заявлять об устойчивом преимуществе `1.12× быстрее` на основании одного прогона.

## Размер бандла

`npm run analyze` — CI-гейт размера: gzip каждого артефакта должен быть не больше **100 КБ**. Для каждого entry печатаются raw, gzip и Brotli. `size-limit` оставлен только для локального просмотра с информационным бюджетом 250 КБ raw на entry.

| Артефакт | Raw | Gzip | Brotli |
|---|---:|---:|---:|
| `dist/index.js` (универсальный, ESM) | 173.8 KB | 45.5 KB | 41.6 KB |
| `dist/index.cjs` (универсальный, CJS) | 174.8 KB | 46.0 KB | 42.1 KB |
| `dist/index.node.js` (Node, ESM) | 173.7 KB | 45.3 KB | 41.5 KB |
| `dist/index.node.cjs` (Node, CJS) | 175.0 KB | 45.9 KB | 42.0 KB |
| `dist/index.browser.js` (браузер, ESM) | 173.8 KB | 45.5 KB | 41.6 KB |
| `dist/index.browser.cjs` (браузер, CJS) | 174.8 KB | 46.0 KB | 42.1 KB |

Файлы `.d.ts` и `.d.cts` добавляют примерно по 7 КБ и не проверяются `analyze.mjs`.

Начиная с v1.1.0 таблица kanji (Unicode → Shift JIS) — литерал `Uint16Array` (6953 записи), а не base64 с декодированием через `Buffer`, чтобы поддерживать браузерные рантаймы. Ранее сообщённый примерный raw-размер бандла вырос с 88 КБ до 174 КБ; gzip вырос с 39 КБ до 46 КБ, чистый прирост около 7 КБ.

## Уже применённые оптимизации

- **Таблицы GF(256):** предвычисленная antilog-таблица на 512 элементов убирает операции остатка из горячего пути умножения.
- **Полиномы генератора Рида — Соломона:** мемоизация по длине EC, без повторного построения для каждого блока.
- **Штраф N3:** скользящие 11-битные окна сканируют строки и столбцы за линейное время.
- **Кандидаты масок:** применение/отмена XOR-маски вместо копирования целых матриц; штрафы включают format-биты.
- **SVG:** горизонтальные серии тёмных модулей сливаются в один `<path>`.
- **PNG:** Node использует `node:zlib` с уровнем сжатия 9; браузер — `CompressionStream('deflate')` с подключением reader'а до записи.

## Память

Символ QR версии 40 содержит 177 × 177 модулей. Пиковое выделение оценивается в несколько мегабайт — в основном булева матрица и промежуточные битовые массивы. Постоянные кэши — полиномы генератора Рида — Соломона и таблицы GF(256). Это оценки реализации, а не измеренные бенчмарки памяти.

## Как улучшить воспроизводимость бенчмарка

Текущая история из двух прогонов полезна для первичного сравнения, но недостаточна для детекции регрессий. Будущим обновлениям `scripts/bench.mjs` и `benchmarks/history.json` стоит записывать:

1. **Идентичность:** версию схемы, метку времени, версию пакета, git-коммит и статус «грязного» рабочего дерева.
2. **Окружение:** версии Node и V8, ОС/архитектуру, модель CPU и факт запуска в CI.
3. **Конфигурацию:** итерации прогрева, измеряемые итерации на вход, независимые повторы и точные идентификаторы нагрузок.
4. **Статистику:** тайминги по повторам плюс медиану и вариативность; производные отношения должны указывать направление (например, `fabQrMs / qrcodeMs`, где значения меньше 1 означают, что `fab-qr` быстрее).
5. **Baseline:** явно указанный релиз или коммит, измеренный в сопоставимых условиях.
6. **Хранение и схему:** документированную JSON-схему и политику хранения истории либо архивируемые CI-артефакты.

**Не** заполняйте новые статистические поля выдуманными значениями и не считайте два исторических прогона достаточными для расчёта устойчивых оценок дисперсии. CI-гейт на регрессию производительности следует вводить только после того, как бенчмарк будет проверен на повторяемость на сопоставимом железе.

## Воспроизведение

```bash
git clone https://github.com/zammartin2/qr
cd qr
npm install
npm run bench      # дописывает новую запись в benchmarks/history.json
npm run analyze
```

Коммитьте обновлённый `benchmarks/history.json`, когда новый записанный прогон должен стать частью отслеживаемой истории производительности проекта.
